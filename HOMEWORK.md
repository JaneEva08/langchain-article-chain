## 1. Задание

1. Создать собственную цепочку из 3–4 звеньев для конкретной задачи (статья, код, анализ данных, отчёт).
2. Описать логику шагов.
3. Реализовать цепочку на Python с LangChain.
4. Минимальная структура: анализ задачи → подбор инструментов → реализация → проверка/ревью.
5. Сдать ссылкой на GitHub, архивом или скриншотами работы цепочки.

**Моя задача для цепочки:** по теме получить готовую статью в Markdown.

### Звенья

| № | Звено | Вход | Выход |
|---|---|---|---|
| 1 | `analysis_chain` — анализ задания | тема | JSON: цель, аудитория, ключевые вопросы, тон |
| 2 | `outline_chain` — структура статьи | JSON анализа | JSON: заголовок, разделы с тезисами, вывод |
| 3 | `draft_chain` — реализация | анализ + структура | статья в Markdown |
| 4 | `review_chain` — проверка/ревью | список замечаний + статья | исправленная статья |

Каждое звено получает только нужные ему данные: звено 3 не видит исходную тему, только анализ и план. Звено 4 вызывается только если локальная проверка нашла замечания (нет заголовка `#`, не все разделы плана, статья короче порога). Исправление принимается, только если замечаний стало меньше.

## 6. Выводы

1. **Цепочка даёт контроль над промежуточными результатами.** В `steps.json` видно, что выдал анализ и какой план получился, и можно понять, на каком звене пошло не так. В одном запросе этого не видно.
2. **Результат нестабилен даже при низкой температуре.** Один и тот же запрос «Как начать работать с Docker» дал статьи в 1214 и 697 слов, с 7 и 6 разделами. Чем жёстче шаги и ограничения в промптах, тем меньше разброс, но на двух запусках вывод предварительный.
3. **Дешёвая проверка перед запросом к модели экономит вызовы.** В трёх обычных прогонах локальная проверка ничего не нашла, и звено 4 не потребовало запроса. Платный запрос к модели в ревью нужен только при реальных замечаниях.
4. **Ревью надо принимать только по метрике.** Правка принимается, если замечаний стало меньше. Без этого модель могла бы «улучшить» статью в худшую сторону.
5. **Блоки кода в тексте уязвимы к очистке ответа.** Код урока для снятия ограждений пригоден для генерации кода, но не для статьи. После исправления в статье про Docker сохранились все блоки кода.
6. **Разбор урока по шагам выявил ошибки, которые на первый взгляд не видны:** ключ в коде, имя файла из латиницы, нечитаемый лог. Они не мешают демо, но ломаются в реальных проектах.

Выборка небольшая: четыре прогона на одной модели. Выводы 2 и 3 — наблюдения, а не измерения.

Задание этого не требовало, это граница проверки, а не недоработки:

- нет `Tools` из LangChain (поиск, чтение файлов): цепочка работает от темы, а не от внешних источников;

- качество статей оценено по структуре, объёму и наличию блоков кода, а не по фактической точности содержания: команды и пояснения я не проверяла по документации Docker.
